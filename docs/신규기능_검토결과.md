## 2. 확인된 법정 기준 (공식 출처)

> 아래는 **공식 자료로 확인된 사실**입니다. 이후 판단의 근거로 사용합니다.

**주휴수당 발생 요건 3가지** (고용노동부 고객상담센터)

1. 근로기준법상 근로자일 것
2. **4주를 평균하여 1주 소정근로시간이 15시간 이상**일 것
3. **1주간의 소정근로일을 개근**할 것

**핵심 개념**

- **소정근로시간** = 근로계약 당시 약속된 시간 (실제 근무한 시간이 아님)
- **소정근로일** = 근로계약 당시 일하기로 약속한 날

**근로기준법 제18조 제3항** — 4주 평균 1주 소정근로시간이 15시간 미만인 단시간근로자에게는 제55조(주휴일)와 제60조(연차)를 적용하지 않음

> 출처: [고용노동부 고객상담센터 — 주휴수당 지급기준](https://1350.moel.go.kr/rtmview.do?id=1000059852) · [국가법령정보센터 — 근로기준법](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=265959)

### ⚠️ 기존 기획의 수정 필요 사항

현재 README에 주휴수당 조건이 **"주 15시간 이상 대상"** 으로만 적혀 있습니다. 정확하지 않습니다.

- ❌ "주 15시간 이상이면 주휴수당 대상"
- ✅ "4주 평균 **소정**근로시간 15시간 이상 **+ 소정근로일 개근**"

**우리 서비스가 계약서만으로 판정할 수 있는 것은 ①번(15시간 요건)뿐입니다.** 개근 여부는 계약서에 없습니다. 따라서 검증 결과 문구를 이렇게 바꿔야 합니다.

> "계약상 주 소정근로시간이 18시간이므로 **주휴수당 지급 대상 조건 중 시간 요건을 충족**합니다. 실제 지급은 소정근로일 개근 여부에 따라 결정됩니다. 계약서에 주휴수당 조항이 없습니다."

이 수정은 **B를 제외하더라도 반드시 반영해야 합니다.** (현재 문구는 오답 위험)

## 3. 아이디어별 평가

## A. 계약서 기반 질의응답 챗봇 → ③ MVP 이후

### 질문 유형별 분해

| 유형 | 예시 | 답변 방식 | LLM 필요? | 검증코드 필요? | 공식근거 필요? | 오답 위험 | MVP 포함 |
|---|---|---|---|---|---|---|---|
| **1. 계약서 사실 조회** | "급여일은 언제인가요?" | 추출된 JSON에서 값 조회 | **불필요** (템플릿으로 충분) | 불필요 | 불필요 | 낮음 | 가능하나 **불필요** |
| **2. 계산으로 답하는 질문** | "예상 월급은?" | 검증 코드 계산 결과 출력 | 불필요 (설명 문장에만) | **필수** | 기준값 필요 | 낮음 | **이미 구현됨** |
| **3. 사실관계·법률 해석** | "이 상황에서 신고할 수 있나요?" | 답할 수 없음 | — | — | 필수 | **높음** | **불가** |

### 왜 연기하는가

**유형 1·2는 이미 결과 화면이 답하고 있습니다.** 시급·근로시간·급여일이 카드로 표시되고, 예상 월급도 계산되어 나옵니다. 챗봇은 **같은 정보를 다른 UI로 한 번 더 보여주는 것**에 불과합니다.

**유형 3은 우리가 답하면 안 되는 영역입니다.** "그만두려면 어떻게 하나요"는 계약 형태·수습 여부·사업장 규모에 따라 답이 갈리고, 우리는 그 정보를 갖고 있지 않습니다.

**심사 리스크가 있습니다.** 예선 창의성 항목에서 "AI 챗봇 외 차별점 없음"은 감점 사유입니다. 페어사인의 강점은 "AI가 판정하지 않는다"인데, 챗봇을 전면에 두면 그 서사가 흐려집니다.

### 만약 넣는다면 (시간이 남을 경우에만)

자유 입력창이 아니라 **정형 질문 버튼 3개**로 축소합니다.

```
[주휴수당 대상인가요?] [예상 월급은?] [빠진 조항이 있나요?]
```

- 답변은 **추출된 JSON + 검증 결과에서만** 생성
- 계약서에 없는 항목은 **"계약서에서 확인되지 않습니다"** 고정 문구
- 자유 질문은 받지 않음 (법률 상담 오인 차단)

### 추측 방지 설계 (연기하더라도 원칙은 유지)

- LLM에는 **추출된 JSON과 검증 결과만** 전달하고, 계약서 원문 전체를 넘기지 않음
- 시스템 프롬프트에 "제공된 JSON에 없는 항목은 반드시 '계약서에서 확인되지 않습니다'로 답한다" 명시
- 답변 생성 후 **숫자가 검증 결과에 없는 값이면 차단**하는 후처리 검사

## B. 대타 근무 시 주휴수당 판단 → ④ 제외

### 판단에 필요한 사실관계 (목록화)

| 항목 | 어디서 오는가 | 우리가 알 수 있는가 |
|---|---|---|
| 계약상 소정근로일 | 계약서 | ✅ |
| 계약상 주 소정근로시간 | 계약서 | ✅ |
| 4주 평균 소정근로시간 | 계약서 | ✅ |
| 해당 주 실제 출근 내역 | 사용자 입력 | △ (자기신고) |
| **본인이 빠진 날의 성격** | 사실관계 | ❌ |
| **근무일 교환에 대한 사전 합의 여부** | 사실관계 | ❌ |
| **사업주 귀책 여부** | 사실관계 | ❌ |
| **근무표가 공식 변경되었는지** | 사실관계 | ❌ |
| 연차 사용 여부 | 사실관계 | ❌ |

### '대타' 5가지 경우 — 결론이 갈립니다

사용자가 제시한 5가지 경우(① 남이 대신 근무 ② 내가 남 대신 근무 ③ 근무일 교환 ④ 결근 후 보충 ⑤ 근무표 자체 변경)는 **"소정근로일을 개근했는가"의 판정이 서로 다릅니다.**

핵심 쟁점은 "근무일을 바꾼 것이 **소정근로일 자체의 변경**인가, 아니면 **소정근로일에 결근한 것**인가"입니다. 이는 사전 합의의 존재·형태, 근무표 변경의 공식성 등 사실관계에 달려 있고, **행정해석과 사안별 판단이 필요한 영역**입니다.

> ⚠️ **공식 자료 확인 필요 항목**: 근무일 교환 시 개근 인정 여부에 관한 고용노동부 행정해석. 본 검토에서는 확인하지 못했으며, **확인 전까지 어떤 결론도 코드에 넣어서는 안 됩니다.**

### 제외 사유

1. **코드로 확정 판정이 불가능합니다.** 필요한 사실관계 5개 중 우리가 확보할 수 있는 게 없습니다.
2. **오답 피해가 큽니다.** "받을 수 있다"고 답했는데 못 받으면 사용자가 사장과 분쟁을 겪습니다. "못 받는다"고 답했는데 받을 수 있었다면 권리를 포기하게 만듭니다.
3. **법률 상담 서비스로 명확히 넘어갑니다.** 기존 원칙("법률 상담이라고 과장하지 않는다")과 정면 충돌합니다.
4. **개발 공수가 높습니다.** 근무 기록 입력 UI + 일정 관리 DB가 필요한데, 이건 별도 서비스 규모입니다.

### 대안 — 이 정도까지만

주휴수당 결과 화면에 **안내 문구 한 줄**을 넣습니다. 개발 비용 거의 0.

> "실제 지급은 소정근로일 개근 여부에 따라 달라집니다. 대타·근무일 교환 등 개별 상황은 고용노동부 고객상담센터(☎1350)에서 확인하실 수 있습니다."

이것만으로 "우리는 한계를 안다"는 신뢰를 주면서, 오답 위험은 0입니다. **Q&A에서 "대타는 어떻게 하나요?"가 나오면 이 설계를 답으로 제시하세요.**

## C. 알바생 직접 작성 → ② 축소하여 MVP에 추가

### 접근 1 vs 접근 2 비교

| 기준 | 접근 1 (MVP 이후) | **접근 2 (수동 입력 폼과 통합)** |
|---|---|---|
| 추가 개발량 | 0 | **낮음** — OCR 실패 폴백 폼을 그대로 재사용 |
| 기존 화면 재사용 | — | **높음** — 확인·수정 화면이 곧 입력 화면 |
| 데모 가치 | 낮음 | **중간** — "계약서를 못 받았어도" 한 문장 추가 |
| 문제 크기 | — | **큼** (미작성 19.5%) |
| 법적·운영 위험 | 없음 | **중간** — 일방 작성 문서의 오인 위험 |
| 알바생 주도성 | 낮음 | **높음** |
| 전자서명 연결 | — | **동일 모듈 재사용** |
| 완주 가능성 | 높음 | **높음** (폼 하나 추가) |

**→ 접근 2 채택.** 결정적 이유는 **어차피 OCR 실패 폴백 폼을 만들어야 하기 때문**입니다. 같은 폼을 진입점만 다르게 노출하면 됩니다.

```
OCR 3회 실패 → "직접 입력하기" ─┐
                                ├→ 동일한 입력 폼 → 동일한 검증 → 동일한 서명
"계약서를 못 받았어요" 버튼 ────┘
```

### 위험 통제 — 문서 상태 4단계

일방 작성 문서가 체결된 계약서로 보이면 안 됩니다.

| 상태 | 화면 명칭 | 표시 문구 | 가능한 행동 | 시각 표시 |
|---|---|---|---|---|
| 1 | **작성 중** | "아직 상대방에게 보내지 않았습니다" | 수정, 삭제, 확인 요청 보내기 | 회색 뱃지 |
| 2 | **확인 요청됨** | "**내가 입력한 내용**입니다. 사장님 확인 전이며 계약 효력이 없습니다" | 회수, 재발송 | 주황 뱃지 + **전체 워터마크 "확인 전 초안"** |
| 3 | **조건 확인됨** | "양쪽이 내용을 확인했습니다. 서명 전입니다" | 서명 요청, 수정 재요청 | 파랑 뱃지 |
| 4 | **체결 완료** | "양쪽이 서명한 계약서입니다" | 다운로드, 보관함 | 초록 뱃지 + 서명 정보 |

**절대 규칙**

- 상태 1·2 문서에는 **PDF 다운로드 시에도 "확인 전 초안" 워터마크**가 찍혀야 합니다
- 상태 2 문서를 "계약서"라고 부르지 않습니다 → **"근로조건 확인 요청서"**
- 사장에게 가는 링크 첫 화면에 "**알바생이 입력한 내용입니다. 사실과 다르면 수정해주세요**" 고정 표시

### 개인정보 최소화

| 항목 | MVP 수집 여부 |
|---|---|
| 주민등록번호 | **수집 안 함** (전자서명 단계에서 필요하면 그때 검토 — 확인 필요) |
| 주소 | **수집 안 함** |
| 이름 | 수집 (계약 당사자 표기에 필수) |
| 연락처 | 서명 요청 발송용으로만, **발송 후 즉시 마스킹 표시** |
| 계약서 이미지 | 처리 후 **24시간 뒤 자동 삭제** (또는 사용자 요청 시 즉시) |

> 데모용이므로 "저장하지 않음"을 기본값으로 하고, 보관함은 세션 단위로 유지하는 것도 검토할 것.

| 개인정보 위험 | 낮음 | 중간 | **중간** |

### 점수 근거

**A (27점)** — 데이터는 이미 확보되어 있고(추출 JSON) 재사용성이 높아 구현은 쉽습니다. 그러나 **기존 결과 화면과 기능이 중복**되어 적합성 2점, 자유 질문을 받는 순간 법률 상담 영역으로 넘어가 안전성 2점입니다.

**B (16점)** — 모든 항목에서 낮습니다. 판정에 필요한 사실관계를 확보할 수 없고(데이터 1점), 코드로 확정할 수 없으며(오류 통제 1점), 오답 시 사용자가 실제 손해를 봅니다(안전성 1점). **총점과 무관하게 오답 피해 위험만으로 제외 사유가 됩니다.**

**C (44점)** — 문제 크기가 크고(미작성 19.5%), 어차피 만들 폴백 폼을 재사용하므로 공수가 낮습니다. 유일한 감점은 **일방 작성 문서의 오인 위험**인데, 위 상태 4단계 설계로 통제 가능하다고 판단해 안전성 3점을 주었습니다.

## 6. 권장 사용자 흐름

기존 흐름을 유지하고 **진입점만 두 개**로 늘립니다.

```
                  ┌─ [계약서를 받았어요] → 사진 업로드 → AI 추출 ─┐
   시작 화면 ─────┤                                              ├→ 확인·수정 화면
                  └─ [아직 못 받았어요] → 직접 입력 ─────────────┘   (동일 화면)
                                                                        ↓
                                                          법정 기준 검증 (코드)
                                                                        ↓
                                                          결과 + 쉬운 설명 (AI)
                                                                        ↓
                                                          계약서 / 확인요청서 생성
                                                                        ↓
                                                          상대방에게 전송
                                                                        ↓
                                                          전자서명 → 체결 완료
```

**화면 수는 늘지 않습니다.** 시작 화면에 버튼 하나가 추가될 뿐이고, 이후는 완전히 동일합니다.

## 7. 챗봇 답변 안전 원칙

> A를 나중에 구현하더라도 아래 원칙은 **결과 화면의 설명 문구에도 그대로 적용**합니다.

1. **계약서에 있는 사실과 법정 기준을 구분한다**
   - "귀하의 계약서에는 시급 10,000원으로 기재되어 있습니다" (사실)
   - "2026년 최저임금은 10,320원입니다" (기준)
2. **계산 결과와 AI 설명을 구분한다** — 숫자는 검증 코드 출력만 사용. AI가 만든 숫자는 화면에 띄우지 않는다
3. **정보가 부족하면 확인 질문을 한다** — 답을 추정하지 않는다
4. **불확실한 경우 조건부로 안내한다** — "~라면 ~일 수 있습니다" 형태, 단정하지 않는다
5. **공식 근거를 표시한다** — 근로기준법 조문 번호, 고용노동부 자료 출처
6. **적용 기준일을 표시한다** — "2026년 기준" 명시. 최저임금은 매년 바뀐다
7. **계약서에 없는 내용은 추측하지 않는다** — 고정 문구 "계약서에서 확인되지 않습니다"
8. **개별 분쟁의 법률적 결론을 단정하지 않는다** — "신고 가능 여부", "부당해고 여부" 등은 답하지 않는다
9. **필요 시 공식 상담기관을 안내한다** — 고용노동부 고객상담센터 ☎1350
10. **답변에 사용한 입력값을 표시한다** — "주 18시간 · 시급 10,000원 기준으로 계산했습니다"

### 화면에 상시 노출할 문구

> 이 서비스는 법정 기준을 자동으로 계산해 알려드립니다. 법률 자문이 아니며, 개별 상황에 대한 판단은 고용노동부 고객상담센터(1350) 또는 전문가와 상담하시기 바랍니다.

## 10. 최종 권고안

### A. 계약서 기반 챗봇 → **③ MVP 이후로 연기**

유형 1·2 질문은 이미 결과 화면이 답하고 있어 기능이 중복됩니다. 유형 3은 우리가 답해서는 안 되는 법률 판단 영역입니다. 챗봇을 전면에 두면 "AI가 판정하지 않는다"는 우리 차별점이 오히려 흐려집니다.

### B. 대타·주휴수당 판단 → **④ 제외**

판정에 필요한 사실관계(사전 합의 여부, 근무표 변경의 공식성 등)를 서비스가 확보할 방법이 없습니다. 오답 시 사용자가 임금을 못 받거나 사장과 불필요한 분쟁을 겪는 실질적 피해가 발생합니다. 대신 "개별 상황은 1350으로 확인하세요" 안내 한 줄로 한계를 정직하게 드러내는 편이 신뢰에 유리합니다.

### C. 알바생 직접 작성 → **② 축소하여 MVP에 추가**

미작성 19.5%라는 가장 큰 사용자군을 커버하고, OCR 실패 폴백 폼을 재사용하므로 추가 개발이 사실상 진입점 버튼 하나입니다. 다만 일방 작성 문서가 체결 계약서로 오인되지 않도록 **문서 상태 4단계와 "확인 전 초안" 워터마크를 반드시 함께** 구현해야 하며, 이 통제 장치 없이는 넣지 않는 편이 낫습니다.
