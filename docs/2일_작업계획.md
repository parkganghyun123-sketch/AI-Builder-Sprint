# Day 1

## D — 프론트 API 연결 (최우선, 팀 전체의 병목)

D가 막히면 나머지 셋의 작업이 데모에 안 보인다. 오늘 여기에 화력을 집중한다.

### D-1. `/contracts/extract` 를 api.ts 에 추가

현재 `web/lib/api.ts` 에 이 엔드포인트만 빠져 있다. 파일 업로드라 `FormData` 를 쓴다.

```ts
export async function extractContract(file: File): Promise<ContractTerms> {
  const form = new FormData();
  form.append("file", file);
  const res = await fetch(`${BASE}/contracts/extract`, {
    method: "POST",
    body: form,          // Content-Type 을 직접 넣지 말 것 (boundary 가 깨진다)
  });
  if (!res.ok) throw new Error(await res.text());
  return res.json();
}
```

응답 형태는 `spikes/full_pipeline.py` 를 돌리면 실물로 볼 수 있다.

### D-2. mock 제거 — 화면 순서대로

`upload → review → result → sign → complete` 순으로 하나씩 실제 호출로 바꾼다.
한 화면 끝날 때마다 실제로 눌러보고 다음으로 넘어갈 것. 한꺼번에 바꾸면 어디서 깨졌는지 못 찾는다.

- `upload` → `extractContract(file)`  ⚠️ Upstage 응답에 **20초쯤 걸린다.** 로딩 표시 필수
- `review` → 추출 결과 표시·수정 (아래 D-3)
- `result` → `POST /contracts/validate`
- `sign`   → `POST /contracts/analyze-sign`
- `complete` → `GET /contracts/{id}/status` 폴링

### D-3. review 화면 — 이 제품의 핵심

AI가 잘못 읽은 값을 사용자가 고치는 자리다. 여기가 "AI는 읽기만 한다"를 눈으로 보여준다.

- `confidence === "LOW"` → 강조 표시, 확인 유도
- `confidence === "NOT_FOUND"` → 빈칸 + 입력 유도
- `source_text` → "계약서에서 이렇게 읽었어요" 로 함께 표시
- 모든 항목 수정 가능

`source_text` 는 백엔드에서 23개 필드 전부 채워져 온다. 안 쓰면 아까운 값이다.

### D-4. 409 처리

`analyze-sign` 은 위반이 있으면 409로 막는다. `ViolationBlockedError` 가 이미 정의돼 있으니
이걸 잡아 위반 화면을 띄우고, "알고도 진행" 선택 시 `proceed_with_violations: true` 로 재요청한다.

**이 흐름이 데모의 하이라이트다.** 그냥 통과시키지 말 것.

## B — 만 18세 미만 근로시간 규칙

모두싸인 특별상의 약자 보호 가점을 정면으로 겨냥한다.
**코드로 판정 가능한 유일한 약자 항목**이라 킥 ③(판정은 코드)과 결이 맞는다.

### B-1. `constants.py` 에 상수 추가

```python
MINOR_AGE_LIMIT = 18
MINOR_DAILY_HOURS = 7.0        # 근로기준법 제69조
MINOR_WEEKLY_HOURS = 35.0
MINOR_EXT_DAILY_HOURS = 1.0    # 합의 시 연장 한도
MINOR_EXT_WEEKLY_HOURS = 5.0
MINOR_NIGHT_START = "22:00"    # 제70조 — 야간·휴일근로 원칙 금지
MINOR_NIGHT_END = "06:00"
MINOR_SOURCE_ID = "SRC-LSA-69"
MINOR_NIGHT_SOURCE_ID = "SRC-LSA-70"
```

수치는 확인된 값이다. 15세 이상 18세 미만 기준 1일 7시간·1주 35시간,
합의가 있어도 1일 1시간·1주 5시간까지만 연장 가능하다.

### B-2. `rules.py` 에 검사 2개 추가

기존 `check_minimum_wage` 구조를 그대로 따른다.

- `check_minor_working_hours(terms, birth_date)` — 1일 7시간 / 주 35시간 초과
- `check_minor_night_work(terms, birth_date)` — 22시~06시 근무 포함 여부

⚠️ **생년월일이 없으면 검사 자체를 건너뛴다.** `UNKNOWN` 도 만들지 말 것.
미성년자가 아닌 사용자에게 "확인 불가" 항목이 뜨면 노이즈다.

### B-3. 단위 테스트

기존 `validation/tests` 형식대로. 최소 이 경우들.

- 17세 · 1일 8시간 → VIOLATION
- 17세 · 1일 7시간 → OK
- 17세 · 주 35시간 초과 → VIOLATION
- 17세 · 22시~02시 근무 → VIOLATION
- 19세 · 1일 8시간 → 검사 자체가 안 나옴
- 생년월일 없음 → 검사 자체가 안 나옴

### B-4. C와 접점

`ContractTerms` 에 생년월일이 없다. **스키마 변경이 필요하다.**
C와 합의해 `ValidateRequest` / `AnalyzeSignRequest` 에 `worker_birth_date: str | None` 을 추가한다.
계약서에서 추출하는 값이 아니라 사용자가 입력하는 값이므로 `ContractTerms` 안에 넣지 않는다.

## A — 평가 신뢰도 보강

지금 "10장 100%" 는 **합성 이미지 1회 실행** 결과다. 심사에서 "실제 사진은요?" 가 반드시 나온다.

### A-1. 실제 촬영 사진 3장 추가

종이에 인쇄해 휴대폰으로 찍는다. 기울어짐·그림자·구겨짐이 있어야 의미가 있다.
정확도가 떨어져도 **그대로 기록한다.** 낮은 숫자가 100%보다 신뢰를 준다.

### A-2. 평가 3회 반복

추출은 재현되지 않는다. 실제로 같은 사진에서 `contract_start` 가
`"2026년 8월 1 일"` / `"2026년 8월 1일"` 로 갈렸고 confidence 도 HIGH/LOW 로 달랐다.

`evaluate.py` 에 반복 실행 옵션을 넣고 필드별 평균·최저를 낸다.
**"3회 평균 ○%, 최저 ○%" 가 "100%" 보다 강한 발표 자료다.**

### A-3. 판정 안정성 측정 (킥 ③의 결정적 근거)

추출값이 흔들려도 **판정 결과는 같은가**를 측정한다.
같은 사진 3회 → `validate()` 결과가 3회 모두 동일한지.

동일하다면 이것이 **"AI는 읽기만, 판정은 코드"의 실측 증명**이다.
발표에서 이 표 하나면 "환각이면요?" 질문이 끝난다.

### C-1. D의 연결 지원 (오늘 최우선)

D가 API 붙이다 막히면 즉시 대응한다. C 본인 작업보다 이게 우선이다.

### C-2. 생년월일 필드 추가 (B와 합의 후)

`schemas.py` 의 `ValidateRequest` / `AnalyzeSignRequest` 에 `worker_birth_date` 추가.
`/contracts/validate`, `/contracts/analyze-sign` 에서 B의 검사로 넘긴다.

### C-3. 데모 중 재배포 금지 규칙 공유

`_store` 가 메모리라 **재배포하면 계약 상태가 전부 날아간다.**
실제로 오늘 이 문제로 문서 상태를 잃었다.

팀 전체에 공유할 것: **데모 시작 전에 배포를 끝내고, 시연 중에는 누구도 push 하지 않는다.**

`ValidationReport` 의 숫자 집합과 문장의 숫자를 대조하는 함수 하나. 30분.

# 킥 ① — MVP와 병렬로 진행

원래 Day 2 오전에 뒀으나, 그러면 MVP가 하루 밀릴 때 킥이 통째로 날아간다.
**킥 ①은 D의 화면 작업과 의존관계가 거의 없다.** 입력이 `ValidationReport` 하나뿐이라
프론트 없이도 만들 수 있다. 그래서 Day 1부터 병렬로 돌린다.

### 담당과 시점

| 작업 | 담당 | 시점 | 비고 |
|---|---|---|---|
| 숫자 검증기 | C | **Day 1** | 문구 생성보다 먼저 |
| 템플릿 버전 | A | **Day 1** | 보험. LLM 없이 동작 |
| LLM 버전 | A | Day 2 오전 | 템플릿 위에 얹음 |
| 화면 배치 | D | **Day 2 오후** | 카드 하나, 30분 |

**D는 Day 1에 킥 ①에 손대지 않는다.** 화면 연결이 병목이라
여기가 밀리면 킥이 있어도 보여줄 데가 없다.

### 먼저 템플릿 버전을 만든다 (보험)

LLM 없이 판정 결과를 문장 틀에 끼운다.

> "사장님, 계약서 다시 보다가 시급이 최저임금(10,320원)이랑 차이가
> 있어서요. 확인 한 번 부탁드려도 될까요?"

숫자를 `ValidationReport` 에서 그대로 가져오므로 환각이 원천 차단된다.
개발 1시간. LLM 버전이 안 되면 이걸로 데모한다.

**심사위원에게는 "AI가 문장을 생성했는가" 보다
"이 서비스가 내가 할 말을 찾아준다" 가 훨씬 크게 와닿는다.**
킥의 본질은 LLM이 아니라 그 발상이다.

`spikes/` 에 스크립트로 먼저 만들어 터미널에서 문장이 나오는지 확인할 것.
프론트를 기다릴 필요가 없다.

### ⚠️ 숫자 검증이 이 기능의 생사를 가른다

생성 문장에 판정 수치가 들어간다.

> "시급이 최저임금(10,320원)이랑 조금 차이가 있어서요"

이 숫자를 LLM이 지어내면 **킥 ③이 그 자리에서 무너진다.** 심사위원이 가장 먼저 찌를 지점이다.

구현: 생성된 문장에서 숫자를 전부 뽑아 `ValidationReport` 안의 값과 대조한다.
없는 숫자가 있으면 **문장을 버리고 템플릿으로 대체**한다. LLM을 다시 부르지 않는다.

`README` 에 이미 "답변 숫자 검사 — 원본에 없는 숫자면 차단" 이 적혀 있다. 그 원칙을 그대로 적용한다.

## 오후 — 발표 준비 + 리허설

### 데모 대본 (실행 순서 그대로)

1. 사진 업로드 → 20초 → 23개 항목 카드
2. LOW 항목 강조 → 사용자가 수정 → **"판정은 사용자가 확인한 값으로 한다"**
3. 검증 → 최저임금 미달·주휴일 누락 (+ 미성년자면 근로시간 초과)
4. 서명 요청 → **409로 막힘** → 이 화면이 하이라이트
5. "알고도 진행" → 메일 → 모바일 서명 → 서명란에 정확히 안착
6. 상태 동기화 로그 → COMPLETED 2/2

### 리허설 (반드시 실제로 돌릴 것)

서명 왕복에 5분씩 걸린다. **당일 처음 돌리면 늦는다.**
최소 2회, 서로 다른 사람 기기로.

### 발표에서 언어화할 것 (개발 불필요)

**킥 ③ — 신뢰할 수 있는 AI**
> "법 판단을 AI에 맡기지 않았습니다. AI는 읽기만, 판정은 검증된 코드와 조문으로."

A-3의 측정 결과를 근거로 제시한다.

**킥 ② — 사장도 지켜준다**
> "우리는 고발 도구가 아니라, 아무도 나쁜 사람이 되지 않게 하는 도구입니다."

화면에 사업주 쪽 이득이 한 줄이라도 보이면 카피가 실체를 얻는다.

**약자 보호 — 판정과 안내의 구분**
> "계산할 수 있는 건 계산하고, 없는 건 지어내지 않습니다."

미성년자는 코드 판정, 장애·외국인은 요청 문구 생성.
이 구분 자체가 설계 철학의 증거다.

# 하지 않을 것

시간을 지키기 위해 명시적으로 버린다.

- **카카오 로그인** — 출생연도는 비즈니스 앱 심사가 필요해 일정 안에 안 끝난다. 생년월일 입력칸으로 대체
- **`_store` DB 영속화** — 데모 중 재배포만 안 하면 문제없다
- **장애·외국인·임신출산 판정** — 계약서로 판정 불가. 요청 문구로만
- **챗봇** — `AGENTS.md` 규칙대로 핵심 흐름 완성 전에는 착수하지 않는다
- **경로 B(직접 입력 폼)** — 화면 1~5가 끝난 뒤에만

병렬 배치로 바꾼 뒤에는 이렇게 된다.

| 킥 | Day 1 종료 시점 확보 여부 | 근거 |
|---|---|---|
| ① 말 꺼내기 | 템플릿 버전 확보 | A가 프론트와 무관하게 작업 |
| ② 사장도 지켜준다 | 개발 불필요 | 발표 카피 + 화면 한 줄 |
| ③ 신뢰할 수 있는 AI | A-3 측정으로 확보 | 구조는 이미 구현됨 |

**Day 1만 지켜지면 킥 셋 다 살아 있다.** Day 2는 다듬는 시간이지 만드는 시간이 아니다.
