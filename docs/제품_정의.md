# 페어사인 — 제품 정의

> 팀 공유용. 발표 자료·화면 문구·README의 기준 문서.
> 작성 2026-07-29. 손글씨 계약서 실측 이후 서사를 다시 잡았다.

---

## 한 문장

> 사회초년생이 계약서를 사진 찍으면, AI가 읽고 코드가 법정 기준을 판정하고,
> **사용자가 확인한 조건으로 표준계약서를 만들어 양측이 전자서명으로 나눠 갖는다.**

---

## 무엇이 바뀌었나

**이전** — "AI가 계약서를 검사해준다"

이 서사의 문제: 심사위원의 관심이 **OCR 정확도**로 쏠린다.
손글씨 계약서 하나만 내밀면 무너진다. 그리고 실제로 손글씨는 완벽히 못 읽는다.

**지금** — "양측이 같은 계약서를 법적 효력 있게 나눠 갖는다"

AI 검사는 **과정**이고, 양측이 계약서를 갖는 것이 **결과**다.
OCR이 틀려도 사용자가 고치면 결과물의 효력은 같다.
급소가 사라진다.

---

## 세 단계는 서로의 전제다

별개 기능을 붙인 게 아니다. 앞 단계 없이는 뒤 단계가 성립하지 않는다.

```
① 판정 ──→ ② 확인 ──→ ③ 교부
```

| 단계 | 하는 일 | 없으면 |
|---|---|---|
| **① 판정** | 최저임금·주휴 시간요건·휴게시간을 코드가 계산 | 사회초년생은 뭐가 부당한지 모른다 |
| **② 확인** | 사용자가 값을 보고 고침 | 틀린 값으로 판정하면 결과를 믿을 수 없다 |
| **③ 교부** | 표준계약서를 만들어 양측이 전자서명 | 판정 결과가 종이 한 장으로 끝난다 |

**②가 핵심이다.** 타협이나 우회가 아니라, 판정을 신뢰할 수 있게 만드는 장치다.

---

## OCR 정확도는 급소가 아니다

우리가 하는 건 사진 속 계약서를 **복사**하는 게 아니다.
확인·수정된 조건으로 **표준계약서를 새로 만들어 양측이 다시 합의**하는 것이다.

| OCR 정확도 | 사용자가 하는 일 | 결과물의 효력 |
|---|---|---|
| 100% | 확인만 | 동일 |
| 70% | 세 개쯤 수정 | 동일 |
| 0% | 전부 입력 (= 경로 B) | 동일 |

**판정의 정확도와 계약서의 법적 효력은 OCR과 무관하다.**

### 진짜 위험은 다른 데 있다

못 읽는 건 사용자가 알아챈다. **잘못 읽고 자신 있어 하면 아무도 모른다.**

그래서 방어를 두 겹으로 뒀다.

**1) 코드가 AI의 확신을 검사한다** (`app/ai/extract.py`)

시급 0원, 시각 `25:00`, 주 9일 같은 불가능한 값은
AI가 HIGH라고 해도 LOW로 강등한다.

**2) 낮은 신뢰도 값으로는 "문제 없음"이라고 말하지 않는다** (`app/validation/rules.py`)

LOW인 값으로 판정하면 `UNKNOWN`(확인 필요)을 낸다.
보수적으로 경고하는 방향은 그대로 두되, **불확실한 값으로 안심시키지 않는다.**

## 확인 관문

실측에서 나온 기준이다. `spikes/fixtures/handwritten_01.png`, 손글씨, 3회 반복.

### 무엇이 걸러지고 무엇이 안 걸러지나

| 실패 | AI 신뢰도 | 코드가 잡나 |
|---|---|---|
| 시급 `10 000` → `0000` | HIGH | ✅ 시급 0원은 불가능 |
| 빈칸에 양식 문구 유출 | HIGH | ✅ 라벨 필터 |
| 이름 `박강현` → `박강헌` | HIGH | ❌ **못 잡는다** |

`박강헌`은 실존할 법한 이름이다. `16,000`도 그럴듯한 시급이다.
**코드가 이상하다고 판단할 근거가 없다.**

### 그래서 항상 확인받는 항목

| 항목 | 이유 |
|---|---|
| 임금 금액·임금 형태 | 그럴듯하게 잘못 읽으면 판정이 뒤집힌다 |
| 근로자 성명·대표자·사업체명 | 계약서에 그대로 인쇄된다 |

**5개로 유지한다.** 늘리면 사용자가 대충 다 눌러서 관문이 무력해진다.

### 서명을 막는 두 가지

```
409 UNCONFIRMED_FIELDS   확인 안 한 항목이 남았다
409 NAME_MISMATCH        계약서 이름과 입력한 이름이 다르다
```

**이름이 다를 때 코드가 고르지 않는다.**
AI가 잘못 읽었을 수도, 사용자가 잘못 입력했을 수도,
종이에 정말 다른 이름이 적혀 있었을 수도 있다. 사용자가 정한다.

## 법적 근거

**근로기준법 제17조** — 사용자는 근로계약서를 서면으로 **교부**해야 한다.
위반 시 500만원 이하 벌금(제114조).

그런데 현실에서는 알바생이 계약서를 못 받는 경우가 흔하다.
사장님만 갖고 있으면 나중에 조건이 달랐다고 다퉈도 근거가 없다.

**전자서명으로 체결하면 양측이 자동으로 같은 계약서를 갖는다.**

| | 얻는 것 |
|---|---|
| 알바생 | 계약서 원본, 분쟁 시 근거 |
| 사장님 | 교부 의무를 이행했다는 증거 |

한쪽 편을 드는 게 아니라 **양쪽 다 안전해진다.**
이것이 "고발 도구가 아니라 아무도 나쁜 사람이 되지 않게 하는 도구"의 실체다.

## 사용자 흐름

```
사진 업로드
   ↓  Upstage Document Parse + Information Extract (20초)
23개 항목 추출
   ↓  코드가 상식 검사 — 불가능한 값은 신뢰도 강등
확인 화면
   ↓  LOW·NOT_FOUND 강조, 원본 사진 대조, 사용자가 수정
법정 기준 판정
   ↓  코드가 계산 (LLM 미사용) — 최저임금·주휴·휴게·필수기재
말 꺼내기 문구
   ↓  판정 결과 → 사장님께 보낼 정중한 문의 메시지
서명 요청
   ↓  409 관문 2개 통과 필요 (미확인 항목 / 이름 불일치)
표준계약서 PDF + 모두싸인
   ↓  근로자 → 사업주 순서 서명
양측이 같은 계약서 보유
```

## 심사 예상 질문과 답

**"손글씨 못 읽으면 어떡하나요?"**

> 고치시면 됩니다. 저희가 파는 건 읽기가 아니라 판정입니다.
> AI가 못 읽어도 최저임금 비교와 주휴 계산은 정확하고,
> 그게 사용자가 혼자서는 못 하는 일입니다.
> 그리고 확인된 조건으로 만든 계약서를 양측이 나눠 갖습니다.

**"AI가 환각을 일으키면요?"**

> 법 판단을 AI에 맡기지 않았습니다. AI는 읽기만, 판정은 코드와 조문으로 합니다.
> 실제로 같은 사진에서 추출값이 흔들려도 판정 결과는 같았습니다.
> 그리고 AI가 자신 있게 틀리는 경우를 실측으로 확인해서,
> 판정에 쓰이는 값은 신뢰도와 무관하게 사용자 확인을 거치게 했습니다.

**"기존 전자계약 서비스와 뭐가 다른가요?"**

> 기존 서비스는 **사장님이 시작**합니다. 저희는 **알바생이 시작**합니다.
> 이미 받은 계약서를 검증하고, 문제가 있으면 고친 뒤 체결합니다.
> 그리고 결과물을 양측이 갖습니다.

**"정확도가 몇 퍼센트인가요?"**

> 합성 이미지 10장은 높게 나옵니다만, 그건 깨끗한 인쇄체 기준입니다.
> 실제 손글씨 1장으로 3회 반복한 결과가 더 의미 있습니다 —
> 19/23이 안정적으로 정확했고, 틀린 항목은 전부 확인 대상으로 표시됐습니다.
> 표본이 적다는 건 저희도 압니다.

## 팀별 반영 사항

**A (AI)** — 추출 프롬프트에 손글씨 대응 명시.
평가셋에 **실제 촬영 손글씨**를 추가할 것. 합성 이미지 정확도만으로는 방어가 안 된다.
정확도는 3회 반복 평균·최저로 보고할 것.

**B (검증)** — LOW 값으로 `OK` 판정을 내지 않는다(`_is_unreliable`).
값이 없으면 `MISSING`은 그대로 — 보수적 경고는 안전한 방향이다.

**C (백엔드)** — 확인 관문, 이름 불일치 차단, 상식 검사 구현 완료.
보관함 목록 엔드포인트가 남았다.

**D (프론트)** — 확인 화면이 이 제품의 핵심이다.

- `POST /contracts/review-items` 의 `reasons` 를 그대로 표시
- **신원 항목은 체크박스가 아니라 입력칸으로.** 값을 미리 채워두고 "맞나요?"라고
  물으면 사람은 그냥 누른다. 빈칸에 직접 쓰게 하면 오류가 사라진다
- **손글씨는 `source_text` 도 AI가 읽은 결과다.** 원본 사진의 해당 위치를 함께 보여줄 것
- 409 두 가지(`UNCONFIRMED_FIELDS`, `NAME_MISMATCH`) 처리
- `archive` 화면 = "양측이 나눠 갖는다"의 화면. 서사의 마지막 장면이다

## 하지 말 것

**"모든 계약서를 완벽히 읽습니다"라고 말하지 않는다.**
손글씨 계약서 하나면 무너진다. 한계를 먼저 말하고 그걸 어떻게 다루는지 보여주는 쪽이 강하다.

**손글씨 폰트로 만든 계약서를 "손글씨 테스트"라고 부르지 않는다.**
폰트는 티가 난다. 어려운 케이스를 피해 간 팀으로 보이면 신뢰가 무너진다.
폰트 샘플은 "글자 모양이 인쇄체가 아닐 때"를 확인하는 용도로만 쓴다.

**판정 문구에 LLM이 만든 숫자를 넣지 않는다.**
`app/bridge/numbers.py` 가 대조한다. 근거 없는 숫자가 있으면 템플릿으로 대체한다.
