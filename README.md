# 페어사인 (FairSign)

> **법을 몰라서 부당한 계약을 맺는 일이 없도록**
> AI가 계약서를 검사하고, 사장님께 할 말을 찾아주고, 그 계약서를 양측이 갖게 합니다

**AI BUILDER SPRINT 2026** · 개발 기간 2026.07.27 ~ 08.03

---

## 3분 시연 방법

1. 메인 화면 우측 하단 챗봇을 열고 `1주일에 12시간 일하면 주휴수당을 받나요?`를 질문합니다.
2. 메인 화면에서 **계약서를 못 받았어요**를 선택하고 근무 요일·시간·임금을 직접 입력합니다.
3. 확인 화면에서 입력값을 검토한 뒤 결과 화면의 법정 기준, 계산식, 말 꺼내기 문구를 확인합니다.
4. 결과 화면 챗봇에서 `계약서에 휴게시간이 안 적혀 있어요`처럼 이어서 질문합니다.
5. 모두싸인 테스트 설정이 있는 경우에만 수정 계약서 미리보기와 전자서명 요청까지 진행합니다.

사진 추출을 재현하려면 JPG·PNG·PDF 형식의 근로계약서를 `/upload`에서 올립니다.
실제 개인정보가 포함된 계약서는 테스트에 사용하지 않습니다.

## 무엇을 만드는가

열여섯 살이 첫 알바 계약서를 받았습니다. 그 앞에는 벽이 세 개 있습니다.

| 벽 | 실제 상황 |
|---|---|
| **모른다** | 최저임금이 얼마인지, 주휴수당 조건이 뭔지 모른다 |
| **말 못 한다** | 알아도 사장님에게 "이거 최저임금 안 맞는데요"라고 못 한다 |
| **증거가 없다** | 계약서는 사장님만 갖고 있어 나중에 다퉈도 근거가 없다 |

페어사인은 이 셋을 차례로 넘습니다.

```
① 알려준다  ──→  ② 말하게 한다  ──→  ③ 남긴다
   법정 기준 판정      사장님께 보낼 문구      양측이 계약서 보유
```

### ① 알려준다 — 뭐가 부당한지

계약서를 사진 찍으면 AI가 23개 항목을 읽고, **코드가** 최저임금·주휴 시간요건·
휴게시간·필수기재를 판정합니다. LLM은 판정에 관여하지 않습니다.

> "시급 10,000원 < 2026년 최저임금 10,320원"

### ② 말하게 한다 — 관계를 지키면서

**진짜 벽은 탐지가 아니라 대면입니다.** 최저임금 미달인 걸 아는 것과,
열여섯 살이 사장님에게 그걸 말하는 것은 전혀 다른 문제입니다.

판정 결과를 **실제로 보낼 수 있는 정중한 문의 메시지**로 바꿔줍니다.

> "사장님, 계약서 다시 보다가 시급이 최저임금(10,320원)이랑 차이가 있어서요.
> 혹시 제가 잘못 본 걸까요?"

고발이 아니라 문의입니다. 사장님이 방어적으로 나오지 않게 여지를 남깁니다.

### ③ 남긴다 — 양측이 같은 계약서를

확인된 조건으로 표준계약서를 만들어 전자서명으로 체결합니다.
**알바생은 계약서를, 사장님은 교부 의무(근로기준법 제17조)를 이행한 증거를 갖습니다.**

판정이 종이 한 장으로 끝나지 않고 법적 효력이 있는 문서로 남습니다.

---

**한 문장**: 확인에서 끝나지 않고, 말을 꺼내게 하고, 계약서가 실제로 바뀌어 양측에 남습니다.

### 사이에 있는 것 — 사용자 확인

①과 ③ 사이에 **사용자가 값을 확인·수정하는 단계**가 있습니다.
AI가 읽은 값을 그대로 판정에 쓰지 않습니다.

이 단계 덕분에 OCR 정확도는 이 서비스의 급소가 아닙니다.
100%면 편하고, 70%면 세 개 고치면 되고, 0%면 다 입력하면 됩니다(경로 B).
**어느 쪽이든 판정의 정확도와 계약서의 효력은 변하지 않습니다.**

⚠️ 위험한 것은 못 읽는 게 아니라 **잘못 읽고 자신 있어 하는 것**입니다.
   그 대비는 [확인 관문](#확인-관문) 참고.

### 두 가지 진입 경로

계약서를 받은 사람과 못 받은 사람이 **같은 검증 엔진**을 씁니다.

| | 경로 A — 서면 계약 (주력) | 경로 B — 구두 계약 |
|---|---|---|
| 상황 | 계약서를 받았는데 내용을 모름 | 계약서를 아예 못 받음 (**미작성 19.5%**) |
| 입력 | 계약서 사진 | 사장님이 말한 조건을 직접 입력 |
| 이후 | 추출 → **검증** → 수정본 생성 → 서명 | 입력 → **검증** → 계약서 생성 → 서명 요청 |

> 경로 B는 입력 방식만 다르고 **검증·생성·서명은 경로 A와 동일한 모듈을 재사용**합니다.
> 추가 개발은 입력 폼 하나뿐입니다.

## 왜 만드는가

- 청소년 알바생 **19.5%가 근로계약서 미작성**
- **경상권 23.5%로 전국 최고**
- 미작성 이유 1위: **"작성해야 하는지 몰라서" (40.4%)**

> 출처: 알바천국 조사(만 15~18세 292명), 2026.05 — [전자신문](https://www.etnews.com/20260526000034)

**"몰라서"가 1위입니다.** 나쁜 마음이 아니라 무지가 원인이라는 뜻이고,
이건 사장님 쪽도 마찬가지입니다. 그래서 우리는 고발 도구를 만들지 않습니다.

### 계약서를 받는 것 자체가 법적 권리다

근로기준법 제17조는 사용자에게 **근로계약서 교부 의무**를 지운다.
위반 시 500만원 이하 벌금(제114조).

그런데 현실에서는 알바생이 계약서를 못 받는 경우가 흔하다.
사장님만 갖고 있으면, 나중에 조건이 달랐다고 다퉈도 근거가 없다.

**전자서명으로 체결하면 양측이 자동으로 같은 계약서를 갖는다.**
알바생은 계약서를, 사장님은 교부 의무를 이행했다는 증거를 갖는다.
한쪽 편을 드는 게 아니라 **양쪽 다 안전해지는** 구조다.

> 출처: [근로기준법 제17조](https://casenote.kr/%EB%B2%95%EB%A0%B9/%EA%B7%BC%EB%A1%9C%EA%B8%B0%EC%A4%80%EB%B2%95/%EC%A0%9C17%EC%A1%B0)

### 기존 서비스와의 관계

| | 기존 | 페어사인 |
|---|---|---|
| 알바 플랫폼 전자계약 | **사장이 시작**해서 계약서를 만듦 | **알바생이 시작**해서 받은 계약서를 검증 |

| 종이 계약서 | 사장님만 보관하는 경우가 많음 | **양측이 같은 문서를 갖는다** |

**전 구간 동작 확인됨** (`spikes/full_pipeline.py`):
사진 → 추출 → 검증 → 계약서 → 서명 요청 → 양측 서명 → 상태 동기화

### 확인 관문

**AI가 읽은 값을 그대로 판정에 쓰지 않는다.** 서명 전에 사람이 확인해야 넘어간다.

실측(`spikes/fixtures/handwritten_01.png`, 손글씨, 3회 반복)에서 드러난 것:

| 실패 | 신뢰도 | 걸러졌나 |
|---|---|---|
| 시급 `10 000` → `0000` | HIGH | ❌ 코드 상식 검사가 LOW로 강등 |
| 이름 `박강현` → `박강헌` | HIGH | ❌ **신뢰도로는 못 걸러진다** |
| 빈칸에 양식 문구 `매월(매주 또는 매일) 일` | HIGH | ❌ 라벨 필터가 제거 |

`박강헌`은 실존할 법한 이름이라 코드가 이상하다고 판단할 근거가 없다.
그래서 **신뢰도와 무관하게 항상 확인받는 항목**을 둔다.

| 항목 | 이유 |
|---|---|
| 임금 금액·형태 | 그럴듯하게 잘못 읽으면 판정이 뒤집힌다 |
| 근로자 성명·대표자·사업체명 | 계약서에 그대로 인쇄된다 |

확인 안 하면 `POST /contracts/analyze-sign` 이 **409 `UNCONFIRMED_FIELDS`** 로 막는다.
계약서의 이름과 입력한 이름이 다르면 **409 `NAME_MISMATCH`** 로 되돌린다 —
어느 쪽이 맞는지 코드는 모르므로 고르지 않는다.

> 확인 항목은 5개로 유지한다. 늘리면 사용자가 대충 다 눌러 관문이 무력해진다.

### 1. 계약 조건 입력

**경로 A (주력)** — 계약서 사진에서 조건을 자동 추출해 카드로 보여줍니다. 잘못 읽힌 항목은 **사용자가 직접 수정**합니다.

**경로 B** — 계약서를 못 받은 경우, 사장님이 말한 조건(시급·요일·시간 등)을 폼으로 직접 입력합니다. AI는 쓰지 않습니다.

두 경로 모두 결과물은 **동일한 형식의 조건 JSON**이며, 이후 단계는 완전히 같습니다.

### 2. 법정 기준 자동 검증

확정된 조건을 법정 기준과 대조합니다.

- **최저임금** — 2026년 시급 10,320원
- **주휴수당 시간 요건** — 4주 평균 1주 **소정**근로시간 15시간 이상
- **휴게시간** — 4시간당 30분 / 8시간당 1시간
- **필수 기재사항 누락 여부** — 근로기준법 제17조

> ⚠️ **주휴수당 판정 범위 주의**
> 주휴수당 발생 요건은 ①근로자 ②4주 평균 소정근로시간 15시간 이상 ③**소정근로일 개근** 세 가지입니다.
> 계약서로 확인 가능한 것은 ②번뿐이므로, 우리는 **"시간 요건 충족"까지만** 판정합니다.
>
> - ❌ "주휴수당 대상입니다"
> - ✅ "주휴수당 지급 대상 조건 중 **시간 요건을 충족**합니다. 실제 지급은 소정근로일 개근 여부에 따라 결정됩니다."
>
> 출처: [고용노동부 고객상담센터](https://1350.moel.go.kr/rtmview.do?id=1000059852) · [근로기준법 제18조·제55조](https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=265959)

> **이 판정은 AI가 아니라 일반 코드로 수행합니다.** 아래 [AI 사용 위치](#ai-사용-위치) 참고.

### 3. 계약서 생성 + 전자서명 체결

표준근로계약서 양식에 확정된 조건을 채워 문서를 만들고, 전자서명으로 양쪽이 체결한 뒤 보관합니다.

### 4. 계약 비서 챗봇 (근거 추적형)

계약서를 검증한 뒤, 사용자가 자기 계약에 대해 물어볼 수 있습니다.

**핵심 원칙: LLM은 사실·판정을 만들지 않고, 분류와 근거 안의 설명만 담당합니다.**

```
사용자 질문
   ↓
[코드] 범위 밖·사실관계 의존 질문 차단 + 개인정보 없는 폐쇄형 특징만 추출
   ↓
[AI]  폐쇄형 특징의 의도·주제 분류 — 정해진 enum 중 하나로만
   ↓
   ├─ FIELD_LOOKUP    → 추출 JSON 조회
   ├─ CALCULATION     → 검증 엔진 호출
   ├─ MISSING_CLAUSE  → 표준양식 diff
   ├─ LEGAL_STANDARD  → 법정 기준 상수 조회
   └─ OUT_OF_SCOPE    → 거절 + 1350 안내
   ↓
결정론적 답변 템플릿 조립 (값은 계약 JSON·검증 결과·KB 상수에서만)
   ↓
[코드] 검증된 KB 스냅샷에서 질문별 상위 근거 검색 (로컬 lexical retrieval)
   ↓
[GPT] 비식별 사실 카드·검증 KB에서 사용할 근거와 설명 순서 선택
   ↓
[코드] strict 스키마 + 사실·KB·출처 관계 검사 후 승인 문구로 조립
   ↓ 통과                         ↓ 실패
맞춤 설명 표시                 Upstage 승인 설명 조립
                                  ↓ 실패
                              결정론적 템플릿
   ↓
답변 카드 표시 (근거 3종 + 행동 버튼)
```

검색 코퍼스는 `KB.md`에서 검토된 KB 항목과 `source_id`를 명시적으로 옮긴 항목으로만
구성합니다. 작은 폐쇄형 코퍼스이므로 벡터DB·임베딩 대신 로컬 키워드 점수 검색을
사용합니다. 임의 웹 문서나 모델 기억을 근거로 추가하지 않으며, 응답에는 실제 검색된
`kb_id`와 `source_id`가 남습니다.

현재 계약 조건 지표로 주휴·퇴직급여·연차·해고예고·수습 최저임금과 보험별
4대보험 확인사항을 지원합니다. 연장·야간수당 계산과 개별 법적 자격 확정은 지원하지
않습니다.

계약서를 올리기 전 메인 화면의 일반 질문도 지원합니다. 로컬 검색기가 표현을 정규화하고
동의어·복합 단서를 확장해 검증된 KB 10개 주제(최저임금, 계약서, 휴게, 미성년 근로,
주휴, 퇴직급여, 연차, 해고예고, 수습 최저임금, 4대보험)에서 관련 항목을 찾습니다.
검색 점수가 낮거나 두 주제가 비슷하면 임의로 고르지 않고 범위 밖으로 처리합니다.
질문 원문이나 개인정보는 외부 모델에 보내지 않고, 필요한 경우 코드가 추출한 비식별
신호와 검색된 ID만 전달합니다. 사용자에게 보이는 법적 기준과 확인 항목은 코드에 등록된
문구만 사용하므로 개인의 지급 대상·가입 대상이나 금액을 임의로 확정하지 않습니다.

#### ChatGPT와 무엇이 다른가

| | ChatGPT | 페어사인 |
|---|---|---|
| 숫자의 출처 | LLM 생성 | **검증 코드 계산 결과만** |
| 재현성 | 물을 때마다 달라짐 | **판정·숫자는 항상 같고 설명 생성 실패 시 안전 템플릿** |
| 근거 | "일반적으로…" | **계약서 조항 + 법령 조문 + 계산식** |
| 모르는 것 | 그럴듯하게 답함 | **거절 + 1350 안내** |
| 답변 이후 | 대화 종료 | **행동 버튼** → 수정본 생성 → 서명 |

> **거절이 기능입니다.** "신고할 수 있나요?"에 ChatGPT는 답하고, 우리는 답하지 않습니다.

#### 답변 카드 구성 (필수 4요소)

1. **결론** — 단정 표현 금지, 판정 범위 명시
2. **근거 3종** — 계약서 위치 / 법령 조문 + 기준일 / 계산식
3. **한계 표시** — 우리가 판정할 수 없는 부분
4. **행동 버튼** — "이 조항 넣어 수정본 만들기" (ChatGPT에 없는 것)

#### 답하지 않는 질문

개별 분쟁의 법적 결론("신고 가능한가요") · 사실관계가 필요한 판단("대타 썼는데 주휴수당 받나요") · 계약서에 없는 정보 · 일반 상담

→ 고정 거절 문구 + 고용노동부 1350 안내

### 문서 상태 (경로 B 필수 안전장치)

알바생이 혼자 입력한 문서가 **체결된 계약서로 오인되면 안 됩니다.**

| 상태 | 화면 문구 | 가능한 행동 | 표시 |
|---|---|---|---|
| **작성 중** | "아직 상대방에게 보내지 않았습니다" | 수정·삭제·확인 요청 | 회색 |
| **확인 요청됨** | "**내가 입력한 내용**입니다. 사장님 확인 전이며 계약 효력이 없습니다" | 회수·재발송 | 주황 + **워터마크** |
| **조건 확인됨** | "양쪽이 내용을 확인했습니다. 서명 전입니다" | 서명 요청·수정 요청 | 파랑 |
| **체결 완료** | "양쪽이 서명한 계약서입니다" | 다운로드·보관 | 초록 |

**절대 규칙**

- 작성 중·확인 요청 단계 문서는 PDF로 받아도 **"확인 전 초안" 워터마크**가 찍힙니다
- 서명 전 문서는 "계약서"가 아니라 **"근로조건 확인 요청서"**로 부릅니다
- 사장에게 가는 링크 첫 화면에 "알바생이 입력한 내용입니다. 사실과 다르면 수정해주세요" 고정 표시

### MVP 제외 기능

- **무제한 법률 상담 챗봇** — 지원 주제만 RAG 설명하며 개별 법률 판단은 하지 않음
- **대타 근무 시 주휴수당 판단** — 사실관계 확보 불가, 오답 피해 큼. **제외**
  (`OUT_OF_SCOPE`로 분류 → 1350 안내)
- 대화형(챗봇) 조건 입력 · 근무기록 관리 · 다국어 · 주거/관광 계약 확장 · 회원가입

## AI 사용 위치

> 이 프로젝트에서 가장 중요한 설계 원칙입니다.
> **읽고·뽑고·설명만 AI가 하고, 판정은 코드가 합니다.**

| 작업 | 담당 | 사용 API | 입력 → 출력 |
|---|---|---|---|
| 사진에서 글자 읽기 | **AI** | Upstage Document Parse | 이미지 → 텍스트·표 구조 |
| 조건 항목 뽑기 | **AI** | Upstage Information Extract | 텍스트 → 항목 JSON |
| 위반 항목 설명 | **AI** | Upstage Solar LLM | 판정 결과 → 쉬운 말 문장 |
| **질문 의도 분류** | **AI** | Upstage Solar LLM | 원문을 전송하지 않고 로컬에서 추출한 개인정보 없는 폐쇄형 특징 → 허용 의도·주제 enum |
| **챗봇 답변 조립** | **코드** | — | 계약 JSON·검증 결과·KB 상수 → 결정론적 답변 카드 |
| **KB 근거 검색** | **코드** | — | 질문·분류 주제 → 검증된 KB 스냅샷의 상위 근거 (`kb_id`, `source_id`) |
| **근거 제한 맞춤 계획** | **AI** | OpenAI Responses API (`gpt-5.6`) | 비식별 분류 키·검증 KB·코드 사실 카드 → 승인 연결·주장 종류와 사실·KB·출처 ID 및 순서 (`store:false`) |
| **맞춤 설명 검증·조립** | **코드** | Pydantic | 자유 텍스트를 허용하지 않는 strict 스키마와 ID 관계 검사 → 서버가 승인 문구·정확한 사실·KB 원문만 조립 |
| **근거 제한 설명 계획** | **AI** | Upstage Solar LLM | 비식별 분류 키·검증 KB·코드 사실 카드 → 연결 방식·사실 ID·KB 문장 ID·출처 ID (질문 원문·계약서 원문·이름·연락처·생년월일·근무장소 제외) |
| **안전 폴백** | **코드** | — | GPT 실패 → Upstage 근거 제한 설명 → 결정론적 템플릿 순으로 복귀 |
| **법정 기준 판정** | **코드** | — | 항목 JSON → 판정 + 근거 + 계산식 |
| **금액 계산** | **코드** | — | 조건 → 예상 월급·차액 |
| 계약서 생성 | 코드 | — | 조건 + 표준양식 → PDF |
| 전자서명 | 외부 | 모두싸인 API | PDF → 서명 요청 → 완료 |

### 왜 판정을 AI에게 맡기지 않는가

1. **재현성** — 같은 계약서를 넣으면 항상 같은 결과가 나와야 합니다
2. **설명 가능성** — "왜 위반인가"에 조문과 계산식으로 답할 수 있어야 합니다
3. **검증 가능성** — 테스트 코드로 정확성을 증명할 수 있습니다

이것이 범용 LLM 래퍼와 구분되는 핵심입니다. **개발 중 판정 로직에 LLM을 넣지 마세요.**

### AI가 틀렸을 때

| 상황 | 처리 |
|---|---|
| 사진이 흐려 못 읽음 | 재촬영 안내 → 3회 실패 시 수동 입력 폼 |
| 항목을 잘못 뽑음 | 사용자가 화면에서 수정 (기본 흐름에 포함) |
| 설명이 이상함 | 근거 조문·계산식을 항상 함께 표시 |

| 백엔드 | **FastAPI** (Python 3.10+) | B, C |
| 스키마 | **Pydantic** — A↔B 인터페이스 고정 | A, B |
| 검증 엔진 | 순수 Python 함수 + pytest | B |
| AI 호출 | Upstage REST 직접 호출 (`httpx`) | A |
| PDF 생성 | **WeasyPrint** (HTML 템플릿 → PDF) | C |
| 전자서명 | 모두싸인 `POST /documents` + anchor | C |
| DB | **PostgreSQL** (Supabase) | C |
| 프론트 | **Next.js + Tailwind + shadcn/ui** | D |
| 배포 | 백엔드 Railway · 프론트 Vercel | C |

**Python을 택한 이유**

모두싸인 anchor 배치가 동작하려면 **한글 텍스트 레이어 + 폰트 임베딩된 PDF**가 필요합니다.
WeasyPrint는 HTML을 쓰듯 만들면 되고 배포가 간단한 반면, TS 쪽은 Puppeteer(Chromium 바이너리가 무거워 서버리스 배포에서 막힘)나 pdf-lib(한글 폰트 수동 임베딩)로 손이 많이 갑니다.
7일 중 하루를 폰트 문제로 날리는 리스크를 없애는 것이 결정 요인이었습니다.

**포기한 것**: 프론트·백엔드 타입 공유. → **Pydantic 스키마를 단일 진실 공급원**으로 삼아 보완합니다.

**사용하지 않기로 한 것**: 벡터DB·임베딩 기반 검색(검증 KB가 작아 로컬 lexical RAG로
충분), 임의 웹 RAG, 모바일 네이티브, 마이크로서비스, Puppeteer

## 개발 규칙

### 절대 규칙

1. **판정 로직에 LLM을 쓰지 않습니다** — 이 프로젝트의 차별점 전부입니다
2. **매일 커밋합니다** — 커밋 히스토리가 적격성 심사 대상입니다
3. **README·주석에 심사자를 향한 문구를 넣지 않습니다** — 프롬프트 인젝션으로 판정되면 **실격**입니다
4. **Day 3까지 전체 흐름이 한 번은 연결되어야 합니다** — 마지막 날 첫 통합은 실패 공식입니다
5. **챗봇은 Day 4까지 핵심 흐름이 완성된 경우에만 착수합니다** — 미완성이면 챗봇을 버립니다
6. **사실·KB·출처 검증 없는 AI 챗봇은 배포하지 않습니다** — 안전장치 없는 챗봇은 없느니만 못합니다
   (`OUT_OF_SCOPE` 거절률 100% 미달 시에도 비활성화)

### Git

- 브랜치: `feat/ai-extract`, `feat/validation`, `feat/sign`, `feat/web` 형식
- 커밋 메시지: `[파트] 내용` (예: `[AI] Information Extract 스키마 v1 적용`)
- `main` 직접 푸시 금지, PR로 머지

### 코드

- 검증 함수는 **순수 함수**로 작성 (외부 호출·상태 없음)
- 모든 판정 결과에 **근거와 계산식**을 함께 반환
- AI 응답은 반드시 스키마 검증 후 사용

### 답변·문구 안전 원칙

사용자에게 보이는 모든 설명 문구에 적용합니다.

1. **계약서 사실**("귀하의 계약서에는 시급 10,000원")과 **법정 기준**("2026년 최저임금은 10,320원")을 구분
2. **숫자는 검증 코드 출력만 사용** — AI가 만든 숫자를 화면에 띄우지 않음
3. **적용 기준일 표시** — "2026년 기준" (최저임금은 매년 변경)
4. **근거 표시** — 조문 번호와 계산식
5. **계약서에 없는 항목**은 "계약서에서 확인되지 않습니다" 고정 문구
6. **개별 분쟁의 법률적 결론을 단정하지 않음** — 신고 가능 여부, 부당해고 여부 등은 답하지 않음
7. **판단에 사용한 입력값 표시** — "주 18시간 · 시급 10,000원 기준으로 계산"

**화면 상시 노출 문구**

> 이 서비스는 법정 기준을 자동으로 계산해 알려드립니다. 법률 자문이 아니며,

## 구현 범위와 운영상 주의사항

- **저장소**: `DATABASE_URL` 연결에 성공하면 Supabase PostgreSQL을 사용합니다.
  미설정 또는 연결 실패 시 메모리로 폴백하며 재시작 시 계약 이력이 사라집니다.
  현재 상태는 `/health`의 `store`에서 확인합니다.
- **로그인·보관함**: 카카오·JWT 환경변수가 모두 설정된 경우에만 로그인이 켜집니다.
  보관함은 로그인한 소유자의 계약만 조회합니다. 영속 보관 재현에는 카카오 설정과
  PostgreSQL 연결이 모두 필요합니다.
- **전자서명**: 모두싸인 계정과 API 키가 있어야 실제 서명 요청을 보낼 수 있습니다.
  모두싸인은 웹훅 HMAC을 제공하지 않으므로 배포 환경에서는 `WEBHOOK_PATH_TOKEN`으로
  URL을 보호합니다. 완료 상태는 모두싸인 API에서 다시 조회해 확정합니다.
- **PDF**: `backend/Dockerfile`에 WeasyPrint 시스템 라이브러리와
  `fonts-noto-cjk`를 포함합니다. 배포 후 `/health/pdf`에서 한글과 서명 anchor를
  육안 확인합니다.
- **외부 AI 폴백**: OpenAI 설명 생성 실패 시 Upstage, 이어서 검증된 결정론적
  템플릿으로 폴백합니다. Upstage 키가 없으면 사진 추출은 사용할 수 없습니다.
- **법률 판단 범위**: 개별 분쟁의 결론, 대타 근무 시 개근 여부, 실제 주휴수당
  지급 자격처럼 추가 사실관계가 필요한 질문은 확정하지 않고 1350 상담을 안내합니다.
- **데이터 운영**: 실계약서와 운영 키는 저장소에 넣지 않습니다. 대회 이후 테스트 키
  폐기와 계약서 이미지 보관·삭제 정책은 실제 운영 주체가 별도로 확정해야 합니다.
